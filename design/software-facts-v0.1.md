# Nibmark(닙마크) — 첫 버전 설계안

상태: 아래는 구현 전 설계 기록이다. 첫 버전 구현과 GitHub Pages 공개 배포는 완료되었다. 최신 동작과 후속 기능은 [README](../README.md) 및 [문법 안내](../docs/syntax.md)를 기준으로 한다.
작성일: 2026-11-15 (Asia/Seoul)

검토 보완: 프로젝트 기술 독립성, Markdown 렌더링 환경, 라벨 종류와 문법 버전의 구분을 추가했다. 이전 초안의 `software-facts 1` 선언을 `nutrition v1` 제안으로 교체했다. 아직 구현 전이며 확정된 공개 API는 아니다.

## 1. 제품의 목적과 확정 사항

개발자가 자신의 프로젝트를 식품처럼 소개하는 라벨을 재미있게 만들어 README에 붙인다.
Mermaid처럼 텍스트를 입력하면 라벨이 렌더링된다. 웹 편집기가 첫 사용 환경이다.

- 첨부 이미지 오른쪽 New Label의 익숙한 흑백 Nutrition Facts 형태를 기준으로 한다.
- FDA 개정에서 드러나는 정보 위계도 소프트웨어에 맞춰 옮긴다.
- 가장 큰 수치는 Dependencies. 영문 기본, 한국어 전환 지원.
- 첫 버전은 사용자가 넣은 내용을 렌더링한다. 프로젝트 분석, SBOM 가져오기, 취약점 조회는 후속 단계다.
- 입력과 렌더링은 브라우저 안에서 처리한다.
- 대상 프로젝트의 언어·프레임워크·패키지 관리자와 무관하다. 같은 입력 텍스트는 같은 라벨을 만든다. 사용자는 자기 프로젝트에 이 편집기의 개발 도구나 의존성을 설치할 필요가 없다.
- 사용자 문법으로 디자인을 자유롭게 바꾸는 대신, 내용의 역할에 따라 템플릿이 위치·굵기·들여쓰기를 정한다.
- 재미는 익숙한 형식과 소프트웨어 내용의 조합에서 나온다. 기본 라벨에 별도 장식이나 농담을 강제하지 않는다.

제품명은 **Nibmark**, 한국어 표기는 **닙마크**, Markdown 코드 블록 식별자는 **nibmark**로 확정했다(2026-11-15). 라벨 안의 제목은 **Software Facts**로 유지한다. 저장소 초기화 조건은 개인 계정 jhbrunokim, Public, MIT, 별도 nibmark 폴더로 확정했다.

프로젝트 소개 초안은 [README](../README.md), Mermaid README에서 참고한 내용과 착수 준비 상태는 [검토 문서](mermaid-readme-review.md)에 정리했다.

## 2. FDA 라벨의 원리를 옮기는 방법

아래의 식품 라벨 변경 사항은 FDA의 설명에 근거한다. 오른쪽 대응은 이 제품의 설계 제안이며 소프트웨어에 대한 FDA 기준을 뜻하지 않는다.

| 식품 라벨의 표현 원리 | Software Facts의 대응 |
| --- | --- |
| Serving size를 눈에 잘 띄게 표시 | 1 release, 버전, 실행용/전체 의존성 등 수치의 기준을 상단에 배치 |
| Calories와 수치를 크게 강조 | Dependencies와 의존성 수를 가장 큰 수치로 표시 |
| 총량 아래 세부 성분을 표시 | 직접/간접 의존성 및 그 안에 포함된 선택 의존성을 계층으로 표시 |
| Includes Added Sugars로 포함 관계를 명시 | Includes optional처럼 이미 상위 수치에 들어간 부분집합을 들여쓰기 |
| 실제 수량과 %DV를 함께 표시 | 12 packages 같은 수량과 전체 의존성 대비 비율을 함께 표시 |
| 하단 설명으로 %DV의 의미를 분명하게 함 | 분모·반올림·부분집합 포함 여부를 짧은 각주로 설명 |
| 상세 영양소를 하단에 배치 | 라이선스 구성 등 보조 정보를 가는 구분선 아래 배치 |

참고: [FDA — Changes to the Nutrition Facts Label](https://www.fda.gov/food/nutrition-food-labeling-and-critical-foods/changes-nutrition-facts-label), [FDA — What’s on the Nutrition Facts Label](https://www.fda.gov/food/nutrition-facts-label/whats-nutrition-facts-label).

FDA 라벨의 %DV는 권장 섭취량에 대한 비율이다. 여기서는 전체 구성 중 비율을 보여주므로 열 제목은 `% of Total*`로 바꾼다. Dependencies가 많거나 적다는 이유로 등급을 매기지 않는다.

## 3. 시각 설계

검토용 파일: software-facts-label.svg. 예시 수치는 모두 가상이다.

- 흰 바탕, 검은 글자, 직각 외곽선. 배경은 다크 모드에서도 흰색 유지.
- 큰 초굵은 제목, 굵은 기준 단위, 작은 보조 정보, 가장 큰 대표 수치.
- 최상단 제목, 기준 단위, 대표 수치, 비율 열, 본문, 보조 성분, 각주의 순서 고정.
- 수치와 비율은 오른쪽 정렬. 부모 행은 굵게, 자식 행은 들여쓰기.
- 굵은 검은 띠와 가는 행 구분선의 대비를 원본처럼 유지.
- 그라데이션, 둥근 카드, 그림자, 아이콘, 색상 배지 없음.
- 기준 폭 360px, 높이는 내용에 따라 늘어난다. 내보내기 크기는 비율을 유지해 변경.
- 긴 이름은 줄바꿈하고 행 높이를 늘린다. 내용을 자르거나 글자를 무제한 축소하지 않는다.
- 한국어판도 같은 구조를 유지한다. 사용자 입력 문구는 자동 번역하지 않는다.
- 서체의 굵기와 폭은 구현 전반에서 원본과 비교한다. 원본과의 완전 일치는 아직 검증되지 않았다.

## 4. 제안 문법

아래는 문법 명세안이며 동작하는 구현은 아니다. Markdown에서는 nibmark 코드 블록을 사용한다.

````markdown
```nibmark
nutrition v1
project "tiny-app" version "1.0.0"
serving "1 release"
scope "Runtime dependencies"
dependencies 128

group "Dependency composition" of dependencies
  item "Direct" 12
  item "Transitive" 116
    includes "Optional" 16

group "License declarations" of dependencies
  item "MIT" 96
  item "Apache-2.0" 24
  item "Unspecified" 8

note "Made with care. And probably too much coffee."
```
````

### 문법과 의미

- `nutrition v1`: 라벨 종류와 문법 버전. 필수, 첫 번째 비어 있지 않은 주석 외 줄. nutrition은 식품 성분표형, v1은 우리 문법 버전이며 FDA 개정 연도나 프로젝트 버전이 아니다. 첫 버전은 이 조합 하나만 지원한다.
- `project "이름" version "버전"`: 이름 필수, version 절 선택.
- `serving "기준 단위"`: 생략 시 `1 release`.
- `scope "범위"`: 생략 시 `Runtime dependencies`. 첫 버전에서는 사용자가 지정한 설명이며 자동 분석 결과가 아니다.
- `dependencies N`: 대표 수치. 0 이상의 안전한 정수, 필수.
- `group "제목" of dependencies`: 전체 의존성을 분모로 하는 구성 그룹. 1개 이상.
- `  item "항목" N`: 해당 그룹의 구성 항목. 두 칸 들여쓰기.
- `    includes "하위 항목" N`: 바로 앞 item에 포함되는 부분집합. 네 칸 들여쓰기. item이 없으면 오류.
- `note "문구"`: 선택. 자동 생성되는 비율 설명 다음에 표시.
- `#`로 시작하는 줄은 주석. 빈 줄 허용. 탭 들여쓰기는 오류와 수정 안내.
- 문자열은 큰따옴표로 감싸고 `\"`, `\\`, `\n`을 지원. 임의 HTML, CSS, JavaScript 구문은 없음.
- project/serving/scope/dependencies/note는 중복 선언 시 해당 줄에 오류 표시.
- header → project → serving/scope → dependencies → group들 → note 순서. serving/scope는 서로 순서 교환 허용.
- 한 줄에 한 명령. 알려지지 않은 명령·여분 토큰·닫히지 않은 문자열은 줄/열과 함께 안내.

자동 배치 규칙: 첫 group은 본문 성분 영역으로 제목을 시각적으로 생략하고 접근성 설명에 보존한다. 이후 group은 제목을 표시하고 굵은 구분선으로 나뉜 보조 성분 영역에 배치한다. includes는 부모 바로 아래에 `Includes …`로 표시한다. 사용자가 좌표·폰트·선 두께를 입력할 필요가 없다.

## 5. 수치 표현의 작은 규칙

프로젝트 분석은 하지 않지만 표시할 비율과 입력의 일관성은 처리한다.

- 비율은 `항목 수 / dependencies × 100`, 정수 반올림. 원래 수량은 그대로 병기.
- 각 group의 item 합계는 dependencies와 같아야 한다. 일부만 열거하려면 `Other` 또는 `Unspecified` 항목을 명시한다.
- includes 수치는 부모 item 이하이며 부모 합계에 이미 포함되어 있다. group 합계에 다시 더하지 않는다.
- 복수 includes는 서로 겹칠 수 있으므로 합산하지 않는다. 각 수치가 부모 이하인지만 검사한다.
- includes의 오른쪽 비율 역시 전체 dependencies가 분모다. 부모 대비 비율과 혼용하지 않는다.
- dependencies가 0이면 모든 item도 0이며 비율은 `—`로 표시한다.
- 반올림 때문에 합계가 99% 또는 101%가 될 수 있음을 기본 각주에 짧게 설명한다.
- 현재 문법 오류나 수치 모순이 있으면 마지막 유효 미리보기에 이전 상태 표시를 하고 다운로드를 비활성화한다.
- 라이선스 예시는 단일 선언 기준의 가상 분포다. 복합 라이선스를 표현할 때는 `MIT OR Apache-2.0` 같은 전체 표현식을 한 항목으로 입력할 수 있다.
- 단위가 다른 코드 줄 수·용량·커피 잔 수 등을 같은 분모에 섞는 기능은 첫 버전에 넣지 않는다. 자유 문구는 note로 표현한다.

## 6. 사용자 흐름

1. 웹 편집기에 들어오면 예시 문법과 완성된 라벨이 이미 보인다.
2. 왼쪽 문법을 바꾸면 오른쪽 라벨이 즉시 갱신된다.
3. 간단한 영문/한국어 예시와 문법 도움말을 제공한다.
4. SVG 또는 PNG를 내려받는다. 저장한 이미지 파일명에 맞는 Markdown 삽입문을 복사한다.
5. 문법 자체도 텍스트로 저장·불러오기 할 수 있다.

초기 화면에는 가입, 저장소 연결, 파일 업로드, 분석 버튼이 없다. 파일 불러오기는 사용자가 저장해 둔 라벨 문법 텍스트에 한정한다.

웹 편집기에는 기본적으로 `nutrition v1`부터 시작하는 본문만 표시한다. 붙여넣기에서는 단일 nibmark fenced code block으로 감싼 본문도 허용한다. Markdown 전체 문서에서 여러 블록을 찾아 렌더링하는 기능은 후속 플러그인의 범위다. 블록이 여러 개이거나 다른 내용이 섞이면 하나의 라벨 본문 또는 하나의 해당 코드 블록을 입력하도록 안내한다. 텍스트 저장은 본문 형식이며 `.nibmark` 확장자를 제안한다.

GitHub는 자체 지원 문법에 대해서만 코드 블록 렌더링을 제공한다. 우리 문법을 README에 직접 넣으면 자동으로 라벨이 되지 않으므로 첫 버전의 공유 결과물은 이미지다. Markdown 복사 버튼은 이미지 업로드까지 수행하지 않으며 파일을 저장소에 함께 추가하도록 간단히 안내한다. [GitHub — Creating diagrams](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-diagrams)

## 7. 구현 구조 제안

`문법 텍스트 → 선택적 Markdown 코드 블록 제거 → 종류/버전 확인 → 파서 → Label AST → 의미 검증 → 레이아웃 → SVG → PNG/Markdown`

- TypeScript로 문법·모델·렌더러를 분리하고 웹 UI는 React + Vite를 후보로 한다.
- 렌더링 코어는 React 및 대상 프로젝트 파일에 의존하지 않는다. 입력은 문법 문자열과 명시적인 표시 설정이다. UI는 코어를 호출하는 역할만 담당한다.
- nutrition/v1 이외의 종류·버전은 명확한 오류를 표시한다. 알 수 없는 종류를 nutrition으로 추정하거나 최신 버전 문법으로 조용히 해석하지 않는다.
- 단순한 줄 단위 문법으로 시작한다. 파서의 결과는 위치 정보를 가진 AST다.
- 수치 계산은 모델에서, 글자 크기·간격·선·줄바꿈은 렌더러에서 담당한다.
- 미리보기와 SVG 내보내기는 같은 렌더링 결과를 사용한다.
- PNG는 브라우저에서 SVG를 변환한다. 한글·굵은 글자·외곽선이 누락되지 않는지 확인한다.
- 입력 문자는 텍스트로 이스케이프하고 외부 리소스를 참조하지 않는 SVG를 만든다.
- 서버 저장·원격 렌더링·분석 API는 필요 없다. 공개 호스팅은 별도 승인 대상이다.
- 입력 문법은 기본 메모리에 보관한다. 저장은 명시적인 텍스트 다운로드 방식이다.
- 글꼴은 라이선스를 확인한 번들 글꼴 또는 시스템 폰트를 검토한다. SVG를 GitHub에서 봤을 때의 폰트 대체와 한국어 줄바꿈을 출시 전 확인한다.
- 처리 한도 가안: 문법 50KB, item/includes 합계 100개. 초과 시 설명을 표시한다.

## 8. 첫 버전 완료 기준

- 신규 사용자가 예제에서 프로젝트명과 수치를 바꾸고 README용 이미지를 만들 수 있다.
- 첨부 오른쪽 라벨과 나란히 놓았을 때 제목·대표 수치·두꺼운 띠·들여쓰기·각주의 시각적 위계가 일치한다.
- 360px 폭에서 영문/한글, 긴 프로젝트명, 큰 수치가 잘리거나 겹치지 않는다.
- 동일 문법으로 같은 SVG를 생성한다. 렌더링할 때 임의 시간값을 넣지 않는다.
- 직접 12 + 간접 116 = 전체 128, 포함 16은 다시 더하지 않는 예제를 정확히 표시한다.
- 0 분모, 합계 불일치, 부모 없는 includes, 따옴표 오류를 이해하기 쉽게 안내한다.
- 생성된 SVG/PNG를 실제 README에 삽입하는 로컬 예제로 확인하고 공개 저장소 게시 없이 검증한다.
- 문법 입력·편집·렌더링·내보내기 중 사용자 내용을 외부로 전송하지 않는다.
- 키보드로 편집·내보내기 가능. 미리보기에는 텍스트 설명과 접근 가능한 제목을 제공한다.
- 본문 입력과 같은 본문을 감싼 단일 nibmark 코드 블록 입력은 같은 라벨을 생성한다.
- 알려지지 않은 종류/버전, 여러 코드 블록 입력을 오류로 안내한다.
- 별도 Node.js·npm·Python 설치 없이 브라우저에서 사용할 수 있다. 런타임이나 프레임워크를 탐색하지 않는다.

검증은 파서의 오류 위치, 포함 관계/합계/0 처리, 대표 라벨의 시각 비교, SVG/PNG 내보내기, 한글 줄바꿈에 집중한다.

## 9. 단계와 승인 범위

1. 현재: 개인 Public 저장소와 MIT 라이선스로 별도 프로젝트를 초기화한다.
2. 승인 후: 파서·모델·고정 템플릿 렌더러를 구현한다.
3. 실시간 웹 편집기와 예제, 영문/한국어 UI, SVG/PNG/텍스트/Markdown 내보내기를 연결한다.
4. 원본과 디자인 비교 및 수치·오류·내보내기 검증을 마친다.
5. 공개 배포는 주소와 배포 환경을 별도로 정한 뒤 진행한다.

후속 후보: 기존 SBOM → 동일 모델/문법 변환 → npm package-lock.json 분석 → CI/CLI/Markdown 플러그인.
이전 질문에서 선택한 npm 우선·실행용 기본·개발용 전환은 분석 기능을 추가할 때의 선호로 보존한다. 첫 버전에는 분석 기능을 포함하지 않는다.

## 10. 승인 요청 시 확인할 사항

- 이 시각적 방향과 FDA 정보 위계의 소프트웨어 대응이 의도에 맞는가?
- 위 전용 문법과 고정 배치, 수동 입력 기반 첫 버전을 승인하는가?
- 승인 범위는 로컬 구현과 검증이며, 공개 배포·프로젝트 분석은 포함하지 않는다.

설계 산출물만 작성했으며 앱 코드나 패키지 설치는 시작하지 않았다.

## 11. Mermaid 방식 검토와 확장 기준

### 확인한 사실

Mermaid의 Markdown 코드 블록 식별자는 `mermaid`로 유지된다. 내부의 `flowchart`, `sequenceDiagram`, `erDiagram` 등이 도표 종류를 지정한다. 설정 frontmatter가 있는 경우 종류 선언보다 먼저 나타날 수 있다. [Mermaid — Diagram Syntax](https://mermaid.js.org/intro/syntax-reference.html), [Mermaid — User Guide](https://mermaid.js.org/intro/getting-started.html)

Markdown의 코드 블록 정보 문자열 자체가 렌더러를 설치하거나 실행하지는 않는다. 문법을 해석하고 그림을 만드는 통합이 필요하다. [CommonMark — Fenced code blocks](https://spec.commonmark.org/0.31.2/#fenced-code-blocks)

### 제안하는 세 층

| 층 | 표현 | 역할 |
| --- | --- | --- |
| Markdown 식별자 | nibmark | 호스트가 어떤 렌더러에 전달할지 식별 |
| 라벨 종류 | nutrition | 표현할 정보 구조와 레이아웃 계열 선택 |
| 문법 버전 | v1 | 문법 및 해석 규칙 선택 |

블록 안의 project version은 소개할 소프트웨어의 버전으로, 위 문법 버전과 독립적이다.

### 왜 종류 선언을 넣는가?

한 종류만 지원하는 첫 버전에서는 기술적으로 생략할 수 있다. 다만 문법 파일 자체를 식별할 수 있고, 이후 서로 다른 구조의 라벨을 추가해도 기존 파일의 해석이 바뀌지 않는다. 비용은 첫 줄 한 줄이므로 명시적으로 두는 안을 추천한다. 첫 버전부터 여러 종류나 확장 플러그인 시스템을 개발하지 않는다.

- 대상 프로젝트가 Python, Java, Rust, JavaScript 또는 프레임워크 없는 프로젝트라는 이유로 라벨 종류가 달라지지 않는다.
- 다른 색상·폭·영문/한국어·폰트는 표시 설정의 차이이며 새로운 라벨 종류가 아니다. 현재 기본 디자인은 고정한다.
- 과거/현재 Nutrition Facts처럼 같은 데이터의 배치만 달라지는 경우는 향후 layout 옵션을 검토한다.
- 릴리스 두 개의 수치를 나란히 비교하는 등 입력 데이터 구조까지 달라질 때 새로운 종류를 검토한다. 이름과 문법은 필요가 생겼을 때 정하고 지금 지원한다고 약속하지 않는다.
- SBOM이나 lockfile 지원은 입력 변환기의 확장이다. 변환 결과를 기존 nutrition 모델에 넣을 수 있으며 언어별 렌더러는 필요 없다.

### 언어 독립성과 표현 범위

사용자는 어느 언어로 만든 프로젝트든 의존성 수, 분류, 라이선스 항목을 직접 입력할 수 있다. npm이나 특정 라이선스 목록을 전제로 하지 않는다. 기본 설계의 packages 표기는 의존성 항목의 집계 단위이며 설치 여부를 뜻하지 않는다.

다만 첫 버전은 의존성 구성을 표현하는 라벨이다. 코드 언어 점유율, 다운로드 수, 번들 용량 등 서로 다른 단위를 의존성 분모에 넣는 범용 통계 라벨은 아니다. 그런 항목의 지원은 별도 단위/분모 설계를 거쳐 추가한다. 의존성이 없는 프로젝트도 dependencies 0과 0인 구성 항목으로 표현할 수 있다.

### 사용 환경별 결과

| 환경 | 첫 버전의 동작 |
| --- | --- |
| 우리가 만드는 웹 편집기 | 본문 또는 단일 코드 블록을 입력하면 실시간 라벨 표시 |
| GitHub README | 생성한 SVG/PNG를 일반 Markdown 이미지로 삽입 |
| 일반 Markdown 뷰어 | 별도 통합 없이는 코드 블록 그대로 표시 |
| 문서 사이트·IDE | 향후 플러그인/렌더러 통합 시 직접 렌더링 가능 |
| Mermaid 자체 | nibmark는 별개의 문법이므로 Mermaid가 해석하지 않음 |

판단: 코드 블록 이름은 하나로 고정하고, 내부 선언에 종류와 버전을 둔다. 프로젝트 언어별 분기는 만들지 않는다. 공개 배포 전이므로 이전 설계 초안의 헤더를 계속 지원하는 호환 계층은 필요 없다.
